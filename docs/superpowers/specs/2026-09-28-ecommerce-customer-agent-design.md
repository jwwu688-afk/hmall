# Hmall 电商客服 Agent 设计

日期：2026-09-28

状态：设计稿，待项目所有者审阅。本文不包含实现授权。

## 1. 目标与边界

面向商城买家的第一期客服 Agent，回答商品、订单、物流和客服规则问题，并在需要人工处理时创建工单。用户已确认第一期只做咨询和查询，售后转人工；Agent 不取消订单、不修改收货地址、不发起退款或支付。

成功标准：用户能在同一会话中完成商品咨询、查询自己的订单及物流、获得有来源的规则答复；无法解决时能提交包含上下文的人工工单。任何情况下都不能读取其他用户的订单或地址。

目标架构按未来微服务设计，同时允许当前单体 `hm-service` 先提供相同契约的适配接口。

## 2. 仓库现状

- Hmall 现为 Java 11、Spring Boot 2.7.12 的 Maven 单体，包含 `hm-common` 和 `hm-service`。
- 现有 `SearchController` 可按名称、品牌、类目和价格搜索上架商品；`ItemController` 可按 ID 查询商品。
- `OrderController` 有按订单 ID 查询接口，但当前代码只调用 `getById`，没有校验订单归属。因此不能直接作为 Agent 的订单工具接口。
- `OrderLogistics` 已存物流公司和单号，但没有面向买家的物流查询接口，也没有运输节点轨迹。
- 仓库暂无客服规则库、售后流程或人工工单模块；不应在第一期回答中暗示已具备这些能力。
- 参考项目 `deepsearch-agents` 使用 Python DeepAgents 主 Agent、子 Agent、FastAPI 和 WebSocket，但会话检查点仍为内存存储。新服务复用其组织方式，不复用其任意 SQL 执行工具。

## 3. 架构决策

在 Hmall 仓库增加独立 Python `customer-agent-service` 目录，作为可单独部署的微服务；不加入 Maven modules。它使用 DeepAgents 组织主客服 Agent 和专用子 Agent。Spring Boot 网关负责用户认证、会话入口、事件转发与限流；Java 领域服务负责业务数据、订单归属和工单持久化。Agent 只通过受控 HTTP 契约访问领域服务，不直接连接商城数据库。

当前单体阶段，由 `hm-service` 实现同一组内部客服查询接口；以后横向拆分时，适配器分别指向商品、交易、物流和客服服务，Agent 工具签名不变。外部客户端只调用 Hmall 网关，不直接暴露 Python 服务。

### 职责

| 组件 | 职责 |
| --- | --- |
| 网关 / 客服入口 | 登录认证、会话归属、请求限流、对话与事件 API、向 Agent 签发短时限域身份凭证 |
| 主客服 Agent | 识别意图、澄清缺失信息、选择工具或子 Agent、组织回复、决定转人工 |
| 商品助手 | 商品搜索、详情、规格对比；只处理已上架商品 |
| 订单物流助手 | 查询当前用户的订单、订单明细、订单状态和已有物流字段 |
| 规则助手 | 检索已发布的配送、支付、退换货等客服政策，并返回来源版本 |
| 工单工具 | 在 Java 客服服务中创建人工工单，保存摘要和关联会话，不处理售后交易 |
| Java 领域服务 | 执行商品、订单、物流、规则和工单查询；校验用户身份及资源归属 |

简单商品或规则问答由主 Agent 直接使用相应工具；跨领域问题才委派多个子 Agent。第一期不启用通用网络搜索、文件系统写入、任意 SQL 或支付工具，以免外部内容和越权工具影响客服答复。

## 4. 第一期开通的场景

1. **售前咨询**：根据关键词、品牌、类目、价格范围查商品；解释规格、当前价格和库存；比较最多三件候选商品。价格和库存以实时商品接口为准，不靠模型记忆。
2. **订单查询**：列出当前用户近期订单；按订单 ID 查询本人订单状态、商品明细、金额和时间。订单不存在与无权限采用相同的对外提示，不泄露订单是否属于别人。
3. **物流咨询**：展示订单发货状态、物流公司和单号。当前仓库无运输轨迹；只有接入物流平台后才能回答实时节点和预计送达时间。
4. **规则问答**：基于已发布且有生效时间的政策答复支付、配送、退换货常见问题。政策缺失或冲突时提示不确定并建议转人工；不自行承诺退款金额、时效或补偿。
5. **转人工**：当用户明确要求、规则无法确定、工具失败或问题涉及售后操作时，收集必要信息并创建工单。第一期的“转人工”表示工单排队，不承诺实时在线人工接入。工单摘要只保留解决问题所需信息。

## 5. 核心交互与接口契约

### 对外接口（经 Spring Boot 网关）

- `POST /api/customer-service/conversations`：创建会话，返回不含用户信息的 `conversationId`。游客可创建匿名会话，用于商品与公开规则咨询。
- `POST /api/customer-service/conversations/{id}/messages`：提交一条消息，返回 `messageId` 和 `runId`。用户身份由认证上下文决定，请求体不接受 `userId`。
- `GET /api/customer-service/conversations/{id}/events?after={eventId}`：SSE 获取回答片段、工具状态、结束与错误事件；事件带递增 ID，断线后可续读。
- `GET /api/customer-service/conversations/{id}`：获取本人历史消息、引用卡片和工单状态。
- `POST /api/customer-service/conversations/{id}/handoff`：显式请求人工工单。重复请求使用幂等键，避免重复创建。

所有会话接口在网关校验会话归属：登录会话绑定用户 ID，匿名会话绑定安全的匿名会话凭证。订单查询要求登录；游客登录后是否合并历史匿名会话不属于第一期。接口返回结构化错误码。请求和事件带关联追踪 ID；对外事件只显示必要业务进度，不暴露内部提示词、工具原始响应或敏感字段。

### Agent 到 Java 的内部工具接口

- 商品：`searchAvailableItems(filters, pageSize)`、`getAvailableItem(itemId)`。
- 订单：`listMyOrders(pageSize)`、`getMyOrder(orderId)`；返回订单状态、明细和最少必要金额字段。
- 物流：`getMyOrderLogistics(orderId)`；必须经过订单归属校验，只返回发货状态、公司和单号。
- 规则：`searchPublishedPolicies(query, category)`；返回政策 ID、标题、版本、生效时间和匹配段落。
- 工单：`createHandoffTicket(conversationId, reason, summary, orderId?, idempotencyKey)`。

以上为领域契约，不要求最终 Java URL 与工具名称相同。Java 服务不能信任模型传来的 `userId`。网关签发短时、限域的内部委托凭证，Agent 调用 Java 服务时携带；Java 服务验证身份并按所属用户再次检查订单、物流和会话。商品查询可匿名，订单与工单工具必须认证。工具响应采用固定字段、明确的空结果和错误码；大对象由工具层裁剪后再给模型。

## 6. 数据流与状态

买家提交消息后，网关校验登录身份或匿名会话凭证及会话归属，记录用户消息并触发 Agent run。主 Agent 根据问题选择只读工具或子 Agent；Java 业务接口返回事实数据及来源标识；Agent 生成自然语言答案和可展示的商品、订单或政策卡片；事件按序写入会话事件存储并经 SSE 推送。需要人工时创建工单并返回工单编号。

MySQL 保存 `cs_conversation`、`cs_message`、`cs_event`、`cs_ticket`、`cs_policy` 等业务记录，分别负责会话、消息、可续读事件、工单和规则版本。Agent 的检查点使用与当前 DeepAgents/LangGraph 版本兼容的持久化实现；实现前验证依赖与恢复行为。MySQL 消息记录为可恢复的业务事实，检查点丢失时仍可重建有限上下文。长期记忆第一期只保留会话上下文，不自动推断或永久保存用户偏好。

## 7. 错误处理与安全边界

- 商品、订单或规则服务超时：有限次数重试；仍失败则明确说明无法查询，保留会话并提供人工入口。
- 用户未登录却问订单：引导登录，禁止按用户口述的手机号或订单号绕过身份校验。
- 订单不存在或无权访问：统一提示“未找到可查询的订单”，记录内部原因但不向用户透露归属。
- 规则来源冲突或过期：不生成确定性承诺，转人工核实。
- 工单服务失败：不说“已转人工”；返回失败状态并允许用户重试。
- 商品和规则文本视为不可信数据，只能作为回答依据，不能改变 Agent 的工具权限或系统指令。
- 默认屏蔽地址、手机号、支付凭据等不必要字段；日志和执行轨迹脱敏。内部服务调用加身份校验与网络隔离。
- 第一期开通的工具均为只读，唯一写操作是创建工单。Agent 无法调用现有支付、扣库存、商品管理或任意 SQL 接口。

## 8. 商城前端接入

仓库新增 `frontend/html/hmall-portal` 静态商城门户及 Nginx 配置。门户使用 Vue 2、Axios 和传统 HTML 页面；不引入新的前端构建链。第一期增加独立的 `customer-service.html` 与少量专用 CSS/JavaScript，并将共享顶部导航 `js/top.js` 中的“客户服务”改为可访问入口。商品搜索页和订单支付页可带商品 ID 或订单 ID 跳转客服页，但页面参数仅用于预填问题，不能替代后端归属校验。管理后台页面不作为第一期人工接待台；人工工单先以服务端记录和最小状态接口交付。

门户已有 `js/common.js`：普通 Axios 请求走 `/api`，登录 token 存在 `sessionStorage`，默认超时为 2 秒。客服消息采用快速返回 `runId` 的异步提交；事件流使用带 `Authorization` 请求头的 `fetch` 流读取，不直接使用无法附加该请求头的原生 `EventSource`。匿名会话使用服务端签发的安全会话凭证。客服页面处理流中断、重连、继续读取、登录跳转和历史消息恢复；不在前端保存订单敏感详情的长期副本。

`frontend/conf/nginx.conf` 当前把 `/api` 路径转发到 8080 并移除此前缀。当前单体阶段，Spring Boot 对应映射为 `/customer-service/...`；未来微服务阶段由网关保留相同外部 `/api/customer-service/...` 契约。事件流代理配置需关闭响应缓冲并设置适当读超时，避免流式回复被 Nginx 聚合或提前切断。现有商城静态页面有部分尚未实现的后端调用；客服功能验收不依赖这些页面的其他缺口。

## 9. 分阶段交付与验收

### 第一阶段：服务骨架与可信查询

创建 Python Agent 服务、网关入口、商品与本人订单/物流的 Java 客服查询适配接口；建立持久化会话和事件。修正订单查询归属校验后才接入 Agent。

### 第二阶段：规则与人工工单

录入可版本化的客服规则，提供检索和来源展示；建立工单记录与最小人工处理状态接口；完善转人工摘要和失败回退。

### 第三阶段：体验与评测

接入商城聊天入口，展示商品卡片、订单卡片、政策来源、事件进度和工单编号。建立覆盖售前、订单、物流、规则、越权和故障的评测集。

验收门槛：跨用户订单与会话访问测试必须全部拒绝；在预设测试集中，商品和订单事实均来自工具返回值，规则答复带可定位的已发布政策来源；无物流轨迹时不编造运输节点；工单成功与失败状态准确；断线后事件可续读，重启后历史会话可查询。性能目标在接入实际模型、数据和部署环境后通过基线测试确定，不在设计阶段臆定数值。

## 10. 第二期候选能力

在第一期稳定后，再评估退换货申请、取消订单、退款、地址修改、优惠券推荐和实时物流轨迹。这些能力需要新增对应 Java 业务流程、规则校验、用户确认、幂等和审计；不能只靠扩充提示词开通。
